#+title: RadMachine -> Org Logbook Importer
#+author: Ashley Gillman, OpenAI

* Overview

This repository is building a small import-and-review tool for turning
RadMachine activity into draft Org logbook entries.

The intent is not to dump raw API exports into Org. The tool should fetch
structured operational data, infer likely authored logbook entries, render a
draft, and leave the final wording to review and editing.

* What Works Now

Current implemented functionality:

- Nix + direnv development environment
- token-based RadMachine API access via environment variable
- typed client methods for common QA, unit, service event, and service-log RTS
  QA endpoints
- tolerant dataclass mirrors for commonly used RadMachine API objects, while
  preserving raw payloads
- live API probing from the CLI
- live collection of QA session data from =qa/testlistinstances=
- lookup and normalization of linked =unittestcollections= and =units/units=
- initial grouping of same-day same-unit =Linac Monthly ::= sessions into a
  =linac_mqc= candidate
- draft Org rendering for =linac_mqc= candidates
- automated tests for config loading, CLI behavior, collection, grouping, and
  rendering
- sample redacted API payloads under =examples/sample_api_payloads/=

This means the repository can already fetch real monthly linac QA data and emit
draft Org text that is close enough to inspect manually.

* Current CLI Use

Assuming RadMachine config is available and =RADMACHINE_TOKEN= is available via
=direnv=:

#+begin_src sh
direnv allow
python -m radlog.cli --format json
#+end_src

Use =--config path/to/config.toml= to override the default config discovery.

Useful current modes:

- probe API root:

#+begin_src sh
python -m radlog.cli --config config.toml
#+end_src

- collect normalized QA sessions:

#+begin_src sh
python -m radlog.cli \
  --config config.toml \
  --collect qa-sessions \
  --start 2026-03-06 \
  --end 2026-03-06 \
  --param 'unit_test_collection__unit__name=LAx - LinacName'
#+end_src

- collect grouped QA candidates with rendered Org:

#+begin_src sh
python -m radlog.cli \
  --config config.toml \
  --collect qa-candidates \
  --start 2026-03-06 \
  --end 2026-03-06 \
  --param 'unit_test_collection__unit__name=LAx - LinacName' \
  --limit 20
#+end_src

- export raw RadMachine records without transforming them:

#+begin_src sh
python -m radlog.cli \
  --config config.toml \
  --export-raw qa-testlistinstances \
  --limit 100
#+end_src

Raw export mode is for saving or inspecting the exact JSON records returned by
RadMachine. It does not group records, render Org, update logbooks, or write
back to RadMachine. It is useful before developing transformations such as:

- building a report from known API records
- composing a derived test entry from existing test entries
- keeping an audit snapshot before experimenting with write/create features

Filters are passed through as query parameters:

#+begin_src sh
python -m radlog.cli \
  --config config.toml \
  --export-raw qa-testinstances \
  --start 2026-03-01 \
  --end 2026-03-31 \
  --param 'skipped=False' \
  --limit 100
#+end_src

For raw export targets with a known date field, =--start= and =--end= filter
the returned records client-side and add a sensible default ordering if one was
not supplied. This avoids guessing undocumented RadMachine range-filter names.
Explicit =--param ordering=...= values are preserved.

* Current Output Shape

The CLI currently emits JSON with:

- request metadata
- redacted config
- =server= for raw endpoint probes
- =records= for normalized source records
- =candidates= for grouped entries
- =raw_export= for unmodified API records from =--export-raw=
- =report= for structured report output from =--report=

For =linac_mqc= candidates, =rendered_org= now contains the draft Org text.

* Reports

The report path is separate from the Org logbook path. It produces factual
report records rather than authored logbook candidates.

Current report mode:

#+begin_src sh
python -m radlog.cli \
  --report qa \
  --last-week \
  --where 'issue in action,tolerance,comment'
#+end_src

For quick inspection before HTML rendering:

#+begin_src sh
python -m radlog.cli \
  --report qa \
  --last-week \
  --where 'issue in action,tolerance,comment' \
  --render plaintext
#+end_src

For browser inspection without building a separate app:

#+begin_src sh
python -m radlog.cli \
  --report qa \
  --last-week \
  --where 'issue in action,tolerance,comment' \
  --render html-serve
#+end_src

=--render html= writes the same HTML to stdout. =--render html-serve= starts a
temporary localhost server, opens the report in the default browser, and runs
until interrupted with =Ctrl-C=.

Use =--last-day=, =--last-week=, or =--last-month= for common date windows, or
use explicit =--start YYYY-MM-DD --end YYYY-MM-DD= dates.

Report filters use a small =find=-style expression syntax via repeatable
=--where= arguments. Repeated =--where= expressions are combined with
implicit AND.

Supported boolean operators, from highest to lowest precedence:

#+begin_example
( EXPR )
! EXPR
-not EXPR
EXPR1 -a EXPR2
EXPR1 -and EXPR2
EXPR1 EXPR2      # implicit AND
EXPR1 -o EXPR2
EXPR1 -or EXPR2
EXPR1 , EXPR2
#+end_example

Supported predicate operators:

#+begin_example
=
!=
in
not-in
contains
matches
exists
missing
#+end_example

Examples:

#+begin_src sh
python -m radlog.cli \
  --report qa \
  --last-week \
  --where '( issue = action -o issue = tolerance ) -and equipment matches "LA.*|CT.*"' \
  --where 'collection contains Monthly' \
  --render plaintext
#+end_src

By default, =--report qa= collects all QA rows, including normal and skipped
results. Use =--filter-by-results= to narrow that to specific result classes,
for example =--filter-by-results action,tol,comment= for abnormal/comment-only
reports.

For reports submitted by a specific RadMachine user, prefer =--user=. The QA
report pushes that filter down to RadMachine as =created_by__username= before
doing local =--where= filtering:

#+begin_src sh
python -m radlog.cli \
  --report qa \
  --last-week \
  --user gillmanas \
  --filter-by-results all \
  --group-by equipment \
  --render plaintext
#+end_src

HTML and plaintext reports can be grouped by =equipment=, the default, or by
=date=:

#+begin_src sh
python -m radlog.cli \
  --report qa \
  --last-week \
  --group-by date \
  --render html-serve
#+end_src

You can also define named report presets in =config.toml=:

#+begin_src toml
[reports.my-weekly-comments]
type = "qa"
title = "My Weekly Comments"
last = "week"
filter_by_results = "comment"
where = ["commenter = gillmanas, commenter = colleague-user"]
render = "html-serve"
group_by = "equipment"
#+end_src

Comma is a low-precedence OR, matching =find= style. This is equivalent to:

#+begin_src toml
where = ["commenter = gillmanas -or commenter = colleague-user"]
#+end_src

Do not set =user= in this preset unless you also want to restrict collection to
QA submitted by one RadMachine user. =user= and =commenter= are separate
filters.

Then run:

#+begin_src sh
python -m radlog.cli --report my-weekly-comments
#+end_src

Preset time window, renderer, and grouping are defaults, so they can be
overridden:

#+begin_src sh
python -m radlog.cli \
  --report my-weekly-comments \
  --last-month \
  --group-by date \
  --render plaintext
#+end_src

Preset filters are intentionally not merged with CLI filters. If a preset
defines =user=, =filter_by_results=, =where=, or =params=, do not combine it
with =--user=, =--filter-by-results=, =--where=, =--param=, =--limit=, or
=--offset=. Define another preset instead.

If live collection is unexpectedly slow, add =--profile=. It prints collection
counters and timings to stderr without changing the report output:

#+begin_src sh
python -m radlog.cli \
  --report qa \
  --last-week \
  --where 'issue in action,tolerance,comment' \
  --render plaintext \
  --profile
#+end_src

The QA report groups rows by a generic equipment group.
If =--start= / =--end= are omitted, it defaults to the last seven days. It
queries recent QA sessions first and stops once it reaches records older than
the requested start date.

* Examples

The =examples/= directory contains site-specific workflow code that is not part
of the reusable radlog library.

Current examples:

- =examples/quickcheck_constancy_tcc.py=
  - dry-run compiler for a TCC QuickCheck Constancy composite test
  - reads existing monthly dosimetry and QuickCheck sessions
  - extracts QuickCheck serial, CAX output, and monthly output-deviation values
  - emits a JSON draft keyed by target QuickCheck Constancy test slugs
  - does not upload, submit, create, patch, or otherwise mutate RadMachine data

Dry-run with the known example sessions:

#+begin_src sh
python -m examples.quickcheck_constancy_tcc \
  --config config.toml \
  --default-example-sessions
#+end_src

Dry-run by linac/date:

#+begin_src sh
python -m examples.quickcheck_constancy_tcc \
  --config config.toml \
  --linac LAx \
  --date 2026-07-07
#+end_src

The example has =--ui tui= and =--ui gui= entry points for linac/date input.
Duplicate source-session selection is still deliberately conservative: current
code defaults to the latest matching session per collection and reports warnings
in the JSON draft.

* API Model Layer

The Python side keeps a thin mirror of the RadMachine API objects it currently
uses in =radlog/rm_models.py=.

These models are intentionally partial and tolerant:

- known fields are exposed as attributes
- unknown fields are preserved in =raw=
- helper properties expose common concepts such as =remote_id= and
  =performed_at=
- normalized workflow models such as =SourceRecord= are still separate

This means code can move away from ad hoc dictionary access without pretending
the RadMachine API is fully documented or stable.

The lower-level client still exposes =get_json= and =paginate= for probing, but
common endpoints also have typed helpers such as:

- =qa_test_list_instances=
- =qa_test_instances=
- =qa_unit_test_collections=
- =units=
- =service_events=
- =service_log_return_to_service_qa=

* Configuration

Expected local setup:

- copy =config.toml.example= to the user config path, normally
  =~/.config/radlog/config.toml= on macOS/Linux or
  =%APPDATA%\radlog\config.toml= on Windows
- put the RadMachine API token in =[radmachine] token = "...";= CLI JSON output
  redacts this value
- alternatively keep =token_env = "RADMACHINE_TOKEN"= in config and place the
  actual token in a shell environment, password manager, or local =.env=
- if using a local =.env=, let =direnv= load it via =.envrc=
- optionally set =RADLOG_CONFIG= or pass =--config= to use another config file

The user cache path is normally =~/.cache/radlog= on macOS/Linux or
=%LOCALAPPDATA%\radlog\cache= on Windows. Future local metadata caches should
use that location rather than repository-local files.
